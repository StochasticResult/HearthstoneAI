# 连续标准天梯

用户明确要求持续天梯、不设次数或时间配额、正常对局不要打断。0.2 原生界面提供「开始自动天梯」「人机练习」「打完这局停止」「立即停止」。自动天梯通过 stdin 的 `mode=ranked_auto` 进入；人机练习仍只跑一局。

## 运行与停止

- 自动天梯没有局数、对局时长、动作数或累计 API 调用/token 配额。炉石客户端和游戏资源守护跨局保持运行；每局保存真实结果，只回收该局 AI/API 进程、解析状态、模型上下文和文件句柄。间隔 2 秒执行程序内局间维护，通过后退出结算、核对标准模式与完整牌表，再在同一客户端排队。
- 正常赢/输/平继续。三局未复盘只设置 `review_due`，不会停止。连续三败、未完成、未确认动作、未核实起手或清理失败会暂停，等待针对问题的复盘。
- 三连败暂停后，只有复盘回执与当次会话及已完成局数完全一致，才以该局作为下一次连败暂停的计数起点。历史完整连败数与各版本胜率继续保存；普通复盘或重启不会重置暂停条件。
- 已确认同一局进入对手回合、日志已追平且从建议产生以来没有提交记录时，这一步单列为 `expired_decisions`，驱动在下一次己方行动时重新决策。已提交但结果不明的动作保留在未确认记录中。
- 「打完这局停止」只写局后请求，并把焦点交回炉石；控制器在单局返回后读取请求。短暂焦点交接只允许重试明确尚未发送输入的拒绝，不能重放已发送或未确认的动作。
- 「立即停止」、退出应用或触发严重资源保护会终止本次运行。天梯中 AI 故障时先停止有疑问的输入，并保留炉石和独立资源守护。只有真实服务端胜负进入已完成对局统计。主动关掉未结算的客户端会造成实际断线，即使本地记录只有 INCOMPLETE。
- 安装、更新及重启安排在自然局间。活动对局期间可以只读有界记录，在独立源码目录复盘和轻量回放；游戏窗口留给运行中的程序。
- 已确认胜负后的结算没有总等待时长或点击次数配额。程序最多每五秒点击一次已校准的底部继续区域，动画或遮挡期间等待，不因一分钟未跳转就关闭健康客户端。全程核对原 PID 和日志边界，保留资源守护、单次查询超时与停止响应；真实客户端错误仍按故障处理。结算期间收到局后停止也立即生效，不生成一条假的新对局结果。

## 进行中的对局遇到 AI 故障

读完文件和检查大小之间，炉石可以继续写入动作回执或发现选项。解析器以每块 64 KiB、每批最多八块读到当前末尾，批次之间短暂让出 CPU。持续有进度就继续读取。文件换代、截短、长时间无读取进展或身份不明时，禁止使用过期牌面操作。

出牌、攻击等主动作回执迟到时，驱动在同一对局中只读等待。已提交一次并收到新的选项组或待选目标后，从新局面重新决策。回合结束而始终没有提交的建议归入过期项。无法核实原动作时，保留未确认记录以供复盘。

随从攻击已提交、但服务器的下一条动作直接结束回合时，局后程序可从完整的单局记录核对当时的牌面、选项组、攻击双方、玩家交接和最终胜负。有充分证据时在 `review.json` 的 `turn_end_attacks` 单列该次提交，保留原始决策日志。这类提交不计入确认攻击或尚未提交的过期建议。证据缺失或互相矛盾时继续按未确认处理。正常健康局无需启动这次回放。

长回合中，突袭随从只能攻击随从时，模型可看到现有攻击力已足以解掉哪些威胁。若当前只有随从交换和结束回合，模型还可安排两只随从各攻击一个不同目标。程序先发送并核对第一击。在首个攻击者存活、目标死亡、新的公开局面和完整合法菜单均符合预期时，第二击才进入同一套执行与回执检查。任一条件不符就重新决策。原始记录中的 `conditional_attack` 是计划，第二击实际采用时另有一条 `confirmed_attack_plan_v1` 决策和对应回执。

先手换牌后，客户端可能已把本方标为当前玩家，而对手仍在选牌。在同一局已核实我方换牌回执、没有待选的己方操作、服务器仍处于换牌阶段时，驱动低频只读等待。服务器进入首回合后，按正常牌面与合法选项校验再行动。

发现和目标选择分别核对服务端选中实体与客户端的 `SendChoices`。模型返回前选择已自动结算时，程序记住实际结果，并丢弃过期建议。若其他客户端输入已先提交，单独计为 `external_choices`。本程序点击后只有匹配的提交与选中回执才算确认。守护期间等到真实终局后，以已核实的本方身份重放同一份日志中的双方胜负。可确认的结果保存至该局 `held-result.json`，正常计入对应版本战绩，并保留 AI 中途停手、需要复盘的标记。

天梯决策遇到首次 API 网络超时或工作进程超时，会先读完游戏日志，再回到正常的身份、回合和合法动作校验。行动窗口仍有效时才根据当前局面重新请求。若发现已自动结算，程序沿用客户端实际给出的牌。每个请求保留 16 秒网络超时及 18 秒进程上限。连续两次请求均超时则暂停 AI 并保护客户端，收到一次合法模型回复后才重置连续超时计数。超时单列为 `api_timeouts`，模型回复数和时延中位数只统计收到的完整决策。

整份 AI 后台退出时，控制器进入 `holding_match_for_review`。窗口提示保留对局、可手动接手，独立的温度、电源、内存和磁盘保护继续运行。控制器等待本局日志中的真实终局或从已进入的对局稳定返回大厅，期间不发送游戏输入。故障观察本身再报错，或控制进程意外退出时，游戏守护仍由原生应用持有，继续保护原炉石进程。用户可以退出原生应用结束这份保护。普通局后的 AI 回收仍复用原客户端。

## 本地记录与复盘任务

数据目录为 `~/Library/Application Support/HearthstoneAI`。密钥不出现在以下文件中。

| 文件 | 含义 |
|---|---|
| `learning/autoplay-state.json` | 当前连续运行的 ID、PID、状态、已返回局数、最近 16 次运行、复盘进度和停止原因 |
| `learning/match-history.json` | 最近 50 条结果及用量/资源/确认汇总，只有 `WON/LOST/TIED` 才是完成的对局 |
| `learning/review-queue.json` | 最多 10 个待复盘公开局面，不直接把最后一步当作败因 |
| `learning/review-ack.json` | 复盘任务写入当前 `autoplay_id` 和已审查的 `completed_games`；旧 ID 无效 |
| `learning/pause-after-game.json` | 局后停止请求；`reason=user_requested_stop` 尊重用户停止，`reason=review_update` 等待局间更新；消费后删除 |
| `runs/.../run-version.json` | 开局时固定的实际安装代码/原生执行文件指纹及源码提交；后续更新不改变本局归属 |
| `learning/match-stats.sqlite3` | 持久战绩账本，以运行 ID 去重，按版本与天梯/人机分别统计；不保存原始牌局或账号信息 |
| `learning/version-stats.json` | 当前版本统计和最近 100 个版本/模式组合的摘要索引；完整历史仍保存在数据库 |
| `learning/strategy-reviews.sqlite3` | 每三场打法复盘的批次、实际版本与结论，独立于会话的健康复盘回执 |

每 15 分钟的 Codex 心跳任务只复盘新结束对局、分析棋力或真实程序错误；不承担定期清理、资源就绪轮询或资源等待后的启动，不重复报告等待状态。需要修改时先写局后请求，等该局自然结束再改。用户停止或退出后不自动重启。分析是程序规则/策略/执行的改进，不是模型权重微调；游戏与常规资源维护均不依赖聊天或心跳任务。

## 每三局打法复盘

每凑齐三场正式结算的标准天梯，下一次定时复盘按开局顺序处理完整批次。胜、负、平都算一场。批次跨会话和程序升级，每局保留自己的版本。起点已设在 `run-20261102-102924` 之后。重复检查不会消耗批次，历史结果订正会重新进入待复盘集合。

在源码目录先运行 `python3 scripts/strategy_batch.py pending`。当 `due` 为真，运行同一命令加 `--samples`。结合每局公开决策、实际合法备选与服务端确认，复核起手、进攻与防守、资源使用、斩杀和回合时间。记录三局中可用于对照的具体回合。软件按正常局后流程保存最近 64 局的紧凑样本至战绩库的 `strategy_samples` 表。详细日志轮换后，样本仍能用于分析；`partial_log`、省略的备选动作和缺失的旧日志应在结论中注明。

完成分析后用 `python3 scripts/strategy_batch.py record RUN1 RUN2 RUN3 --finding '对局、回合和替代走法' --change '具体优化或维持策略的理由' --validation '验证证据及仍待观察的结果'` 登记，再检查下一批。若不足三场就留到下一次。故障、未确认动作与三连败仍立即处理。只有经过正反例与真实局面回放支持的修改才在自然局间部署，随后按版本观察同类决策与胜率。

## 程序内资源维护

`maintenance.py` 在当前局自然结束、子进程与文件句柄回收后，清理本应用旧运行目录并回收 Python 无引用对象。只保留五局详细记录，不清理操作系统 swap、不关闭其他应用、不触碰进行中的游戏日志。自动天梯锁覆盖维护和等待阶段，防止第二份控制器启动。

局间按当前内存压力、可用内存指标、电源、温度和磁盘余量决定是否排队。系统内存压力正常且可用指标至少 20% 时，原有 swap 占用仅用作诊断。压力处于 warning 时，程序先取间隔约 15 秒的两次系统 Swapouts 计数，用实际页大小换算新写出的数据量。近期换出速率高于 256 MiB/分钟时等待，速率回落或压力恢复正常后重新判断。计数缺失、回拨或两次读数相隔过久时重新采样。

可用内存指标低于 20%、内存压力 critical 或未知、磁盘少于 10 GiB、热状态尚未恢复 nominal 或未接电源时，程序进入 `waiting_for_resources`。界面显示具体原因，后台每 15 秒重新判断，已有客户端与游戏守护保持运行，资源恢复后自动续排。

原生应用开始自动天梯时，会在接通电源的 Mac 上申请保持显示器唤醒。系统的请求随应用进程存续，覆盖排队、对局、资源等待、故障复盘和局后更新。下一次启动自动天梯会接续同一份请求。手动停止在本局或立即生效时释放请求，退出应用也会释放。拔电源时组件释放请求，重新接电后根据应用是否还在运行恢复。组件通过系统事件等待电源变化、停止或应用退出，手动锁屏、合盖和系统强制锁定仍由 macOS 处理。

计划更新或故障修复后的恢复继承原运行的 swap 基线，用于比较长期变化。若系统用量已下降，可使用更低的当前基线。用户明确停止后的新会话使用新基线。游戏守护和单局 AI 后台的启动检查与排队使用一致的内存条件。独立开发命令仍执行自己的增长上限。

## 每个版本的胜率

安装器根据实际 runtime 文件、卡牌/策略数据和原生可执行文件生成版本指纹。开局时固定到本局记录；只改文档不会改变代码指纹。软件启动与每局结束在运行记录显示本版天梯战绩，状态文件也保存最新统计。胜率定义为 `胜 / (胜 + 负)`，同时列出胜负样本数、平局和未完成运行；没有胜负样本时显示暂无数据。人机与天梯单独分组，旧日志清理不清除累计统计。

结果按运行 ID 在 SQLite 事务中写入，重复复盘不会重复计数，同一结果订正会更新原记录。统计开始前未保存版本的历史只导入现存的至多 50 条记录，归为 `unversioned`；没有把它们猜配到新版，也不能恢复已删除的更早结果。原始模型名称保存在本地账本中，当前版本汇总包含该版本所用模型的全部结果。可按任意确切版本查询完整历史：`python3 runtime/version_stats.py --version 0.2-实际指纹 --mode ranked`。

## 仍保留的边界

比赛期间普通 swap 增长、20% 内存余量、10 GiB 磁盘余量和 fair 热状态只记录维护需求，等这一局结束后处理。游戏启动时 300–400% CPU 表示多核负载，不能单独认定过热；启动后持续高负载记录供复盘，真实温度另行保护。

紧急保护仍可立即停止：macOS critical 内存压力、未知内存读数、可用内存指标低于 10%、磁盘不足 2 GiB、serious/critical 热状态、游戏 RSS 超过 1800 MiB、AI 进程组超过 200 MiB，或电源、电量与 AI 异常持续 CPU 条件。普通维护与紧急保护不混用。历史 swap 总量不单独阻止启动；所有对局共用原始基线。FPS 临时设为 30，退出恢复。单次请求输入最多 64000 字节、输出 1536 token、网络子进程 18 秒；启动、数据恢复与动作确认的超时不等于对局时长配额。开发命令仍使用原来更严格的即时守护；仅游戏会话启用延后维护。

只保留最近五局详细日志；每局 Power.log 副本 8 MiB、事件 1 MiB、决策 2 MiB、动作输出前缀与末尾合计 4 MiB。日志上限不结束比赛：Power.log 副本满后停止复制，实时解析器继续读原始日志；动作输出保留开局及最近 64 KiB；`decision-summary.json` 持续累计用量、确认与实际结果，最后写入有界汇总。详细记录不全时明确标记，不把缺失确认行误报为未确认动作。时延中位数最多使用最近 256 次，汇总注明样本数。已解析的累计字节不是内存，不再按总读取字节终止；单块、实体、事件和嵌套状态的真实内存边界保留。采样保护不等于内核硬限制；连续运行和完整标准天梯仍需要实际验收。

每局收尾回收该局 AI、API 请求和 AI 守护，显式关闭标准流和日志。长期父进程只保留有界运行列表、界面日志、客户端 PID 和对局日志游标。下一局从排队前的完整行边界开始新解析。源日志身份、PID 或结束结果不符时停止自动点击结算。发现新的 CREATE_GAME 时保护可能已经开始的对局。正常退出、用户停止或严重资源保护按既有规则回收客户端并恢复 FPS。

成功的局间回收记录 `game_preserved=true`、`match_workers_closed=true` 和同一正整数 `game_pid`，此时 `game_closed=false` 是预期行为。复盘与维护不能再把它误当成清理失败。常规清理不强行回收游戏私有缓存，也不清空操作系统 swap；若客户端本身增长，仍按实际资源门槛等待或紧急保护。机制覆盖与尚未验收的输入界面见 `MECHANICS.md`。
